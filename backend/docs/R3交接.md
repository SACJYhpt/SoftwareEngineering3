## 前端需要的 API

沿用 `Authorization: Bearer <access_token>`。既有登入、公開瀏覽、活動建立／修改及報名 URL 不變。錯誤仍為 `{ "detail": { "code": "...", "message": "..." } }`；Pydantic 輸入格式錯誤為標準 422 陣列。

| 方法／路徑 | 輸入或用途 |
|---|---|
| `PATCH /me/profile` | `{department_id, grade}`；不接受 identity／role |
| `PATCH /admin/users/{id}/identity` | `{identity, department_id, grade}`，限系統管理員 |
| `POST /events`、`PATCH /events/{id}` | 原欄位加候補、資格及 `confirm_overlap`，見下方 |
| `POST /events/{id}/registrations` | 無 body；可能正式或候補，重複仍回同一紀錄 |
| `DELETE /events/{id}/registrations/me` | 取消本人正式／候補；仍須由前端二次確認 |
| `POST /events/{id}/registrations/switch` | `{source_event_ids:[...], source_status:"registered"或"waitlisted", confirmed:true}` |
| `POST /events/{id}/registrations/{registration_id}/remove` | `{reason, confirmed:true}`，單位管理者 |
| `POST /events/{id}/cancellation-requests` | `{reason, confirmed:true}`，本人截止後申請 |
| `GET /events/{id}/cancellation-requests` | 單位管理者查申請歷史與 pending |
| `POST /cancellation-requests/{request_id}/review` | `{decision:"approve"或"reject", reason}`，拒絕必填 reason |
| `POST /me/cancellation-action` | `{token}`；**只讀取入口資訊，不取消**；仍須本人登入 |
| `GET /events/{id}/registrations?q=姓名或Email` | 保留 `registrations` 正式名單，加 `waitlist` 與順位、出席欄位；只對正式名單做搜尋 |
| `GET /events/{id}/registrations.csv` | 管理者下載正式名單；同時寫匯出稽核 |
| `GET /events/{id}/attendance` | 從 DB 計算 `registration_count`、`checked_in_count` |
| `POST /events/{id}/registrations/{registration_id}/check-in` | 單人報到，活動當天（台灣日期）且結束前 |
| `DELETE /events/{id}/registrations/{registration_id}/check-in` | 撤銷報到，時間與權限同上 |
| `PATCH /events/{id}/registrations/{registration_id}/attendance` | `{status:"present"或"absent"}`，結束後 7 天內 |
| `GET /admin/audit-logs?page=1&page_size=30` | 管理員讀稽核；沒有更新或刪除 API |

### 建立／修改活動新增欄位

```json
{
  "waitlist_enabled": true,
  "waitlist_capacity": 10,
  "eligibility_identities": ["student"],
  "eligibility_department_ids": [1],
  "eligibility_grades": [3, 4],
  "confirm_overlap": false
}
```

這只是新增欄位示意，不是完整建立活動 body。`department_id`／資格 ID 要查目前 DB 的 `/units` 或 `/departments`，不可把範例的 `1` 當成資工系固定 ID。管理者的主辦單位查 `/auth/me.managed_units`。

候補開啟時省略 `waitlist_capacity`，後端會以 `(capacity + 1) // 2` 計算。資格未設或空陣列表示該類條件不限。活動沒有資格限制時 `eligibility_description` 回「不限」。

同單位撞期時，第一次回 `SCHEDULE_OVERLAP_CONFIRMATION_REQUIRED`（409），`detail.conflicts` 有名稱與時間；前端顯示後讓管理者確認，再帶 `confirm_overlap:true` 送相同資料。第一次沒有儲存，不需要刪除重試留下的活動。

### 報名回應

正式仍回 `status:"registered"`；候補回 `status:"waitlisted"`、`waitlist_position`、`waitlist_count`。共通欄位保留：`registration_id`、`event_id`、`registered_at`、`registration_count`、`capacity`、`already_registered`。

新報名／候補回 201，重複有效報名／候補回 200，不新增紀錄或重寄確認信。保留舊的 `registered_count` 與 `registration_status` 相容欄位。

活動詳情與個人活動增加：候補設定、資格、`waitlist_position`、`can_cancel_registration`、`can_request_cancellation`、`cancellation_request`。本人狀態可能是「已報名」「候補第 N 位」「取消申請審核中」「已取消」「未遞補」；不要只靠解析中文字判斷操作權限，優先用旗標與結構化資料。

撞期回 `TIME_CONFLICT` 或 `WAITLIST_CONFLICT`。`detail.conflicts[]` 有 `event_id`、名稱、時間、`status`、候補順位、`registration_closed`、`action`、`action_path`。前端只能讓使用者放棄這次操作或明確確認切換；不能默默取消原活動。

正式改報名要求新活動取得正式名額，不能默默降成候補；新活動額滿、資格不符或還有其他撞期時，原報名保留。放棄候補的切換可以加入新活動正式名單或候補；原候補若已遞補，回 `SOURCE_STATUS_CHANGED`，必須重新讓使用者確認正式報名的處理方式。

### 提醒信取消入口

信件使用 `/events/{id}#cancel_token=...`。這個片段不會送到 HTTP 存取日誌，前端要讀取後清掉網址，再以登入憑證呼叫 `POST /me/cancellation-action`。

這個 POST 只回傳 `action`、`method`、`path`、`confirmation_required`；**不改報名**。顯示確認畫面後才呼叫回傳的取消或申請 API。token 綁定使用者、報名、活動及該次報名版本，不能作為登入憑證，也不能拿別人的連結操作。前端尚未修改，所以這段讀取與確認畫面需由前端負責人串接。

## 資料庫負責人要知道的變更

沿用同一套 SQLAlchemy 與 MySQL／本機 SQLite，沒有第二套資料庫、Redis 或 migration framework。

- `events` 新增：`waitlist_enabled`、`waitlist_capacity`、三個 `eligibility_*` JSON 陣列、`check_in_used`、`notification_revision`。
- `registrations.status` 擴充為 `registered / waitlisted / cancelled / not_promoted`；新增 `waitlisted_at`、`checked_in_at`、`cancellation_reason`、`revision`。原本 `(user_id,event_id)` 唯一鍵保留，取消後再次報名沿用該列並增加版本。
- `outgoing_emails` 新增 `deduplication_key`（可空且唯一）、`kind`、`registration_id`、`event_revision`、`event_start_at`、`registration_revision`、`reschedule_notice`。`status` 額外使用 `cancelled`，表示已過時的提醒不再寄送。
- 新表 `cancellation_requests`：保留各次申請歷史；只有 pending 的 `active_registration_id` 有值且唯一，避免同筆報名多件 pending。
- 新表 `audit_logs`：操作者、時間、action、target 與 JSON details。ORM 更新／刪除會拒絕，API 只讀；沒有清除排程，所以至少保存一年。部署時還應由 DB 權限限制直接修改，不能把應用層保護說成資料庫管理員也無法改。
- 新表 `registration_workflow_locks`：一筆協調鎖資料，確保跨活動撞期判斷、切換、遞補與排程交易不競態。不是使用者功能或另一套 queue。

新資料庫的完整 MySQL DDL 參考：`schema-r3.sql`。**只編譯，沒有對任何 MySQL 執行；不是舊庫升級腳本。** 舊 R2 庫需要資料庫負責人安排 ALTER、狀態 CheckConstraint 更新及 JSON／布林／版本欄位回填；既有正式報名在套用 metadata 對照前不可隨意重建。`create_all()` 不會替舊表加欄位，啟動檢查遇到舊結構會拒絕，沒有自動 reset 或刪除資料。

### 一致性與吞吐量取捨

所有 R3 報名相關寫入先取得 DB 協調鎖，再由小到大鎖活動列，保留既有 MySQL `FOR UPDATE` 與 SQLite `BEGIN IMMEDIATE`。這也保護「同一人同時報名不同的撞期活動」及切換後的遞補，失敗時連信件佇列一起回滾。

這是本次為了正確性採用的簡單設計：**不同活動的報名寫入也會序列化，可能限制大量活動同時報名的吞吐量**。讀取不需要這把鎖；MySQL 真實效能需另外驗收，不能從 SQLite 測試推論正式流量能力。之後若要改成細粒度鎖，須保留跨活動、使用者及候補的競態測試。

## worker 與時間規則

沿用 `worker.py`，每輪先處理 R3 排程，再跑既有備份與寄信；迴圈間隔 5 秒。`--once` 只處理一輪，適合驗證。

R3 排程包括：截止候補結算、24 小時提醒、取消申請二次提醒與自動核准、活動結束後缺席結算。排程可重跑；狀態與唯一郵件鍵防止重複排信。實際執行會有輪詢／服務停機延遲，應在部署時監控 worker，不能把「時間一到」理解成不用啟動背景程式。

寄信仍使用 R2 outbox、初次加三次重試與寄送紀錄。SMTP 成功後才有 `sent_at`；F03 的 72 小時從實際 sent 計算，不從排信時間計算。舊提醒在寄出前會重新檢查活動取消、開始時間及報名版本；已經送交 SMTP 的郵件無法收回，也無法保證外部 SMTP 絕不重複投遞。

## 暫定細節與團隊確認

1. 「有使用報到功能」定義為第一次實際報到，或事後以出席修正 API 明確記錄；只開名單／搜尋不啟用缺席推論。撤銷最後一筆報到也不把使用紀錄清掉。未使用的活動歷史仍是「未記錄」。
2. 身分改成教師／行政人員，年級清空；改成學生必須提供正整數年級。未自行限制最高年級。行政人員必須配行政單位，其餘配學術系所，沿用 R2 規則。
3. 候補因資格或撞期被略過，終態使用 `not_promoted`，保留原因並通知；不保留在候補中卡住名額。截止結算也用此狀態。前端可使用原因區分。
4. 已有候補時，不允許把候補上限降到現有候補人數以下或直接關閉候補，以免默默丟棄名單；需先處理名單。不同種類資格是 AND、同類多值是 OR。這些介面規則應請需求負責人確認。
5. 候補先後以成功取得交易鎖後的 `waitlisted_at` 加 `id` 排序；無法承諾依使用者網路封包到達／按下按鈕的物理時間先後。
6. 取消活動時，該活動仍 pending 的取消申請會一併自動核准，避免永久掛起。活動取消通知仍寄給當時的正式與候補者。
7. 出席修正時間為 `end <= now < end + 7 days`；報到採台灣日期，活動當天且結束前可操作。R3 不提供請假狀態的寫入 API。
8. 正式 SMTP、MySQL、worker 部署與前端串接尚待團隊配置／驗收。本次沒有改成其他寄信服務、部署平台或新增外部 API。
